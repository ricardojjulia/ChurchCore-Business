## I. Context

On 2026-11-14 the tenant-creation path was traced through the source code of all six member apps. Findings (full evidence in the audit document):

- **No app can take a paying customer from sign-up to a working admin login without manual intervention.** Each app creates tenants differently, under a different name (`churches`, `organizations`, `institutions`, `practices`, `org-<uuid>`), with a different lifecycle and different billing.
- **No app creates tenants atomically.** Two apps' provisioning cannot complete at all (ChMS: missing `church_settings` table; Care: owner password discarded and the worker rejects every signup). Academy's "transaction" runs `BEGIN`/`COMMIT` on a connection pool.
- **Live security holes**, including:
  - Orthos: master passwords that open any account, plaintext password storage, a forgeable session cookie and a signup account takeover
  - ChMS: the provisioning script resets passwords of existing users in the shared auth project and writes passwords into committed scripts
  - LMS: an ungated tenant-creation path with CAPTCHA bypass tokens, and tenants able to edit their own billing fields
- **Governance self-attestation failed.** `scripts/pull-and-enforce-directives.py` marks any requirement without a dedicated check as `passed = True; "Verified"`. Every app's ledger therefore reports directives such as COUNCIL-2026-001 REQ-001-01 (RLS) as verified, including Orthos, whose runtime never uses its database.

## II. Owner Decisions (binding)

| # | Decision |
|---|---|
| D1 | **Every member app offers self-serve signup.** No app is sales-only. |
| D2 | **Self-serve signup is identical across the fleet:** same steps, same screens, same copy structure, same look and feel (COUNCIL-2026-014 design system). Only the product name, logo and sub-brand accent (COUNCIL-2026-002) vary. |
| D3 | **Every tenant starts with a 30-day free trial that includes every feature of the highest paid tier.** No feature is withheld during the trial. |

| D7 | **This standard is enforced by automated, blocking gates.** Self-attestation is not accepted as evidence of compliance. |

## III. Ratified Technical Requirements

### `REQ-016-01`: Canonical Tenant Identity & Slug
1. Every tenant MUST have a `fleet_tenant_id` (UUID v4), stored as a unique, non-null column on the app's tenant root row. App-local primary keys MAY remain.
2. Slugs MUST match `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`, 3–30 characters, be unique case-insensitively within the app, and MUST NOT be in the reserved list in `fleet-tenancy.json`. Each app MUST vendor that list byte-for-byte at the path declared in its `.fleet/tenancy.json`.
3. A slug MUST NOT change after the tenant becomes `active`, except through the control plane.

### `REQ-016-02`: Shared Lifecycle State Machine
1. Every tenant root row MUST carry `tenant_status` and `billing_status` with exactly the values and transitions defined in `fleet-tenancy.json`.
2. All status changes MUST go through one transition function per app that rejects illegal transitions and writes an audit event (REQ-016-09).
3. Tenant users (including tenant owners and admins) MUST NOT be able to modify `tenant_status`, `billing_status`, `plan`, `trial_ends_at`, `fleet_tenant_id`, Stripe identifiers or synthetic/demo flags. This MUST be enforced in the database (trigger or column privileges), not only in the UI.

### `REQ-016-03`: One Atomic, Idempotent Provisioning Entry Point
1. Each app MUST have exactly one provisioning implementation, `provisionTenant`, declared in `.fleet/tenancy.json` as `provisioning_modules`. No other non-test, non-migration code may insert tenant root rows (guard check G05).
2. All database writes for a new tenant (root row, first-admin membership and role, default settings, starter data, audit event) MUST commit in **one database transaction**: a `SECURITY DEFINER` function or a single dedicated client. `BEGIN` issued through a pool is prohibited (G04).
3. Provisioning MUST be idempotent on `fleet_tenant_id`: a repeated request returns the existing tenant, and a failed one resumes.
4. External side effects (auth invite, Stripe customer, email, DNS) MUST run after commit through an outbox with retries. Stripe calls MUST send `Idempotency-Key: <fleet_tenant_id>:<operation>`.
5. A tenant MUST remain `provisioning` until every step succeeds. A failure sets `provision_failed` and stores the error.

### `REQ-016-04`: Exactly Two Entry Points, Both Hardened
1. **Self-serve signup** at the route declared as `signup_route`, following REQ-016-05.
2. **Control-plane provisioning**: `POST /api/fleet/tenants`, plus `GET /api/fleet/tenants/{id}` and `POST /api/fleet/tenants/{id}/{suspend|restore|archive}`, authenticated by a signed service credential (HMAC-SHA256 over the body and a timestamp, with a per-app secret and a 5-minute replay window). User sessions MUST NOT be accepted on these routes.
3. Both paths MUST call `provisionTenant`. All other creation paths MUST be removed. This includes LMS legacy `/signup`, Orthos `/onboarding` provisioning, Care console force-complete and the ChMS per-client generated seed scripts.
4. Public signup MUST:
   - require CAPTCHA, with no bypass tokens in production source (G03)
   - rate-limit per IP and per email domain, failing **closed** in production
   - verify the email address before any tenant row is created
5. Seeds, demo resets and CI fixtures MUST refuse to run against production unless an explicit production override flag is passed.

### `REQ-016-05`: Uniform Self-Serve Experience
1. Every app MUST implement the signup, verification, provisioning-progress, set-password, compliance-acknowledgment, trial-banner, trial-email and plan-selection steps exactly as defined in `SELF-SERVE-SIGNUP-SPEC.md`, using the shared fleet signup package once it is published (Implementation Plan, Phase 1).
2. Per-app variation is limited to product name, logo, sub-brand accent token, product-specific compliance acknowledgments (REQ-016-09) and product-specific onboarding checklist items.

### `REQ-016-06`: Subscription, Trial & Conversion
1. Plan keys MUST be exactly the fleet tier keys in `fleet-tenancy.json`. App-specific plan vocabularies (e.g. `starter|growth|enterprise`, `free|standard|premium`, `solo|group`, `basic`) MUST be migrated (G08).
2. Every new tenant MUST start with `billing_status = trialing` for **30 days**, with access to **all** features of the highest tier. No payment card is required to start a trial.
3. At conversion the customer selects a tier through the shared plan-selection screen and fleet Stripe Checkout. Features above the chosen tier lock at conversion, never during the trial.
4. If the trial ends without conversion, the tenant enters `trial_expired`. It is read-only, export is allowed, and conversion is available at any time. It follows the lifecycle in `fleet-tenancy.json` (archive after 30 days, purge 30 days after that). Data MUST NOT be deleted while the customer can still convert.
5. Prices, value metrics and discounts MUST come from `PRICING-SCHEDULE.md`. Stripe webhooks MUST be deduplicated by `event.id`, MUST check every database write for errors, and MUST map Stripe prices only to fleet tier keys.

### `REQ-016-07`: Customer-Owned First Admin; No Operator Passwords
1. The first admin MUST be the customer's own identity. In self-serve signup they set their own password (or passkey) after email verification. In control-plane provisioning they are invited with a single-use link.
2. Operators and scripts MUST NOT set, generate, print, log, email or commit customer passwords.
3. Provisioning MUST NOT modify any existing account other than adding a membership.
4. Platform staff MUST NOT be made members of customer tenants. Support access MUST use an audited, time-boxed support-access mechanism that records a reason.

### `REQ-016-08`: Lifecycle Status Is Enforced
Session and tenant resolution **and** the database tenant helper used by RLS MUST deny write access to any tenant whose `tenant_status` is not `active`. `suspended` and `trial_expired` tenants are read-only, with export allowed. `archived` tenants are inaccessible to tenant users.

### `REQ-016-09`: Audit, Telemetry & Compliance Capture
1. Every lifecycle event listed in `fleet-tenancy.json` MUST be written to an append-only audit log, retained as a tombstone after purge, and reported to the control plane per `TELEMETRY-SPEC.md`.
2. Every signup MUST record acceptance (with document version) of the Terms of Service and Privacy Policy.
3. **ChurchCore Care** MUST capture BAA acceptance before the tenant can store client data.
4. **ChurchCore Academy** MUST capture FERPA/COPPA acknowledgment before student records involving minors are created.

### `REQ-016-10`: Conformance Test & Blocking Guard (Go-Live Gate)
1. Each app MUST commit `.fleet/tenancy.json` (contract), the vendored reserved-slug list and a vendored copy of `scripts/fleet-tenancy-guard.py`.
2. Each app MUST ship an end-to-end **tenancy conformance test** that runs in CI against a real database (no mocked database client) and proves:
   1. self-serve signup end to end
   2. control-plane provisioning, plus idempotent replay
   3. login as the customer admin
   4. isolation between two tenants
   5. 30-day full-feature trial, then conversion via a simulated Stripe event, with replay ignored
   6. trial expiry, giving read-only access
   7. suspend and restore
   8. archive, then purge with no orphaned rows or identities
3. The CI workflow on `main` MUST run both the guard and the conformance test as **required status checks** (branch protection).

### `REQ-016-11`: Credential & Session Hygiene (Phase 0, immediate)
1. No hard-coded passwords, master passwords, backdoors, default credentials or live secrets may exist in any repository's source (G02).
2. Passwords MUST be hashed with argon2id, scrypt or bcrypt (via Supabase Auth where used). Plaintext or reversible storage is prohibited.
3. Session tokens MUST be signed or server-stored and verified on every request. Unsigned client-readable session state is prohibited.
4. Roles and tenant membership MUST NOT be read from user-editable metadata (e.g. Supabase `user_metadata`).
5. Every credential that was ever committed, printed or exposed by a defect identified in the audit MUST be rotated, and the affected accounts forced to reset.

### `REQ-016-12`: Deprovisioning
`suspend → restore`, `archive` (export offered, access removed) and `purge` (30 days after archive) MUST be implemented through the transition function. Purge MUST:
- remove tenant data in one transaction, using cascades from the tenant root or a CI-verified table list
- remove auth identities that belong to no other tenant
- cancel Stripe subscriptions
- preserve audit tombstones

Purge and trial-expiry jobs MUST actually be scheduled.

## IV. Non-Bypassability Clauses

1. **No default pass.** Compliance with this directive is determined only by:
   - `fleet-tenancy-guard.py`, which has no default-pass path, and
   - a green CI run of the conformance test.

   The legacy enforcement engine MUST treat every `BLOCKING` requirement it cannot positively verify as **NOT VERIFIED**. Statements in `ACKNOWLEDGMENTS.md` are not evidence for this directive.
2. **Go-live gate.** No app may onboard a real customer, accept payment, run a public trial or be marketed as available until it is conformant (all guard checks pass and the conformance test is green on `main`). Apps already serving customers MUST complete Phase 0 immediately and reach conformance under the Implementation Plan. They MUST NOT add new provisioning paths in the meantime.
3. **Phase 0 precedence.** Until REQ-016-11 is met in a repository, no other feature work may merge in that repository except security fixes.
4. **Exceptions.** A guard finding may be excepted only by an allowlist entry in `.fleet/tenancy.json` that has a `reason` and an `expires` date no more than 30 days out. Exceptions are void for checks G01 (contract), G06 (entry points), G07 (conformance test), G08 (plan/trial) and for banned credential literals. Expired exceptions fail automatically. Every active exception is listed in the Compliance Matrix.
5. **No evasion.** Rewriting code so that the guard cannot detect it, for example by splitting or encoding strings, renaming files out of the scanned paths, or moving credentials into files outside version control that production then depends on, is a violation in itself. A false positive is resolved by fixing the guard in the control plane or by a time-boxed exception (clause 4), never by obfuscation.
6. **No waivers.** This directive can be relaxed only by a later ratified directive that explicitly amends COUNCIL-2026-016. No session, agent, script or individual may waive it.
7. **Regression is an incident.** A guard or conformance failure on `main` reverts the app to NON-CONFORMANT, blocks deployment, and MUST be fixed before other work resumes.
8. **Agent pre-flight.** Under the Cross-Repo Council Sync Rule, every agent session in an impacted repository MUST surface outstanding COUNCIL-2026-016 failures as blocking before starting other work.
