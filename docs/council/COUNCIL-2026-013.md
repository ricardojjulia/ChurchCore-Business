## 1. Context & Problem Statement

Following the successful vanguard rollout of the **Council Embedded Security Add-On (`COUNCIL-2026-012` / `DIR-2026-EMBEDDED-SEC-001`)** in **ChurchCore Orthos (`v0.19.0`)** and **ChurchCore Care (`v7.1.0`)**, the Office of the Chief Executive and the Testing Council reviewed the verification architecture that proved every security layer works deterministically in CI and local development.

Historically, security checks across repositories varied in depth:
1. **Static Regex Blind Spots in SQL Audits:** Simple regex checks for `ENABLE ROW LEVEL SECURITY` could be fooled by SQL comments (`--` or `/* ... */`), missed `FORCE ROW LEVEL SECURITY`, or failed to notice if a later migration ran `NO FORCE ROW LEVEL SECURITY` or `DROP POLICY`.
2. **Untested Auditor Failure Modes:** Without a built-in negative ("sabotage") self-test, an auditor script could silently pass even if its parser broke.
3. **Inconsistent Application Guardrail Tests:** While individual apps tested business logic, there was no single, standardized 10-point automated test contract across all repositories proving in-process blocking of SQL Injection, XSS, Path Traversal, Command Injection, token-bucket rate limiting, constant-time `crypto.timingSafeEqual` webhook/cron verification, fail-closed unconfigured webhook `POST` rejection (`HTTP 401`), and stack-trace/secret redaction on unhandled exceptions (`INTERNAL_SECURITY_FAIL`).

To ensure every ChurchCore software package maintains identical, mathematically verifiable proof of protection, this directive elevates the **10-Point Embedded Security Test Suite** and **Stateful RLS + In-Memory Sabotage Auditor** to a **mandatory fleet-wide standard**.

## 2. Strategic & Technical Specifications (Mandatory Requirements)

### `REQ-013-01`: Standardized 10-Point Embedded Security Test Suite (`src/__tests__/embedded_security.test.ts`)
Every ChurchCore software package MUST include and execute `src/__tests__/embedded_security.test.ts` (wired into the standard `npm test` / `pnpm test` pipeline) verifying all 10 canonical security invariants:
1. **Schema Validation Rejection (`INVALID_INPUT`):** Rejects malformed inputs with structured field-level error details before business logic executes.
2. **Trusted Edge IP Prioritization:** Verifies `getClientContext()` extracts `x-vercel-forwarded-for` and `x-vercel-ip` ahead of spoofable `x-forwarded-for` headers.
3. **In-Process WAF-Lite Payload Blocking (`THREAT_DETECTED`):** Fires live SQL Injection (`SQL_INJECTION`), Cross-Site Scripting (`XSS_VECTOR`), Path Traversal (`PATH_TRAVERSAL`), and Command Injection (`COMMAND_INJECTION`) payloads into protected actions and asserts immediate in-process rejection.
4. **Per-Isolate Token-Bucket Rate Limiting (`RATE_LIMIT_EXCEEDED`):** Exhausts a configured token bucket and asserts rejection with a positive `retryAfterSeconds`.
5. **Fail-Closed Exception Containment (`INTERNAL_SECURITY_FAIL`):** Forces an action handler to throw an error containing a sensitive connection string (`postgres://secret@host/db`), intercepts `console.error`, and proves that **neither** the returned `ActionResponse` **nor** `console.error` leaks the raw error message or stack trace—logging only the fixed string `[SECURITY] Embedded guardrail evaluation failed closed (INTERNAL_SECURITY_FAIL).`
6. **Constant-Time Cron & Webhook HMAC Verification (CWE-208):** Verifies `isAuthorizedCron()` and `verifyGitHubWebhookSignature()` use `crypto.timingSafeEqual` (including uniform-time dummy comparison when byte lengths differ) and reject missing, wrong-length, or forged signatures.
7. **Public & Feedback Endpoint Threat Rejection (`HTTP 403`):** Sends XSS and SQLi payloads to feedback/public API endpoints and asserts `HTTP 403` with `{ code: 'THREAT_DETECTED', isThreat: true }`.
8. **Fail-Closed Unconfigured Cron/Webhook `POST` Rejection (`HTTP 401`):** Clears `CRON_SECRET` and `WEBHOOK_SECRET` in test memory, sends unauthenticated `POST` requests, and proves endpoints fail closed with `HTTP 401` rather than failing open when environment variables are unset.
9. **High-Value AI/OpenRouter, Governance & Financial Action Protection:** Verifies that AI prompt dispatchers, governance mutations, and financial ledger actions block SQLi/XSS payloads before invoking external LLM gateways or database mutations.
10. **Database Forced RLS & Sabotage Verification:** Invokes the stateful SQL migration evaluator and asserts 100% table coverage plus sabotage detection.

### `REQ-013-02`: Stateful SQL Migration RLS Evaluator (`scripts/audit-rls-isolation.ts`)
Every repository with a `supabase/migrations/` directory MUST implement `auditSqlMigrationsText()` and `runMigrationsAudit()` in `scripts/audit-rls-isolation.ts` (executable via `npm run audit:rls` or `pnpm run audit:rls`):
- **Comment Stripping:** Must strip both multi-line block comments (`/* ... */`) and single-line comments (`-- ...`) prior to statement evaluation.
- **Identifier Normalization:** Must support both quoted (`"public"."table"`) and unquoted (`public.table` or `table`) identifiers.
- **Sequential State Machine:** Must split migrations by `;` in chronological filename order and track per-table state transitions across:
  - `CREATE TABLE [IF NOT EXISTS]`
  - `ALTER TABLE ... ENABLE | DISABLE | FORCE | NO FORCE ROW LEVEL SECURITY`
  - `CREATE POLICY <name> ON <table>`
  - `DROP POLICY [IF EXISTS] <name> ON <table>`
- **100% Pass Criteria:** `passed` is `true` if and only if every discovered public table has `rlsEnabled === true`, `rlsForced === true`, and `policies.size >= 1`.

---

### `REQ-013-03`: Mandatory In-Memory Live Sabotage Self-Test
To prove that the RLS auditor itself can never silently decay into a no-op, both `scripts/audit-rls-isolation.ts` and `src/__tests__/embedded_security.test.ts` MUST execute an in-memory **Live Sabotage Self-Test** on every run:
- Append `ALTER TABLE public.<table> NO FORCE ROW LEVEL SECURITY;` and `DROP POLICY IF EXISTS ... ON public.<table>;` to the combined migration SQL string in memory.
- Run `auditSqlMigrationsText(sabotagedSql)` and assert that `sabotageResult.passed === false`, `sabotageResult.unforcedTables` contains the sabotaged table, and `sabotageResult.unpoliciedTables` contains the sabotaged table.
- If the auditor fails to catch the sabotage, the script MUST exit with non-zero status (`process.exit(1)`).

---

### `REQ-013-04`: Non-Recursive `SECURITY DEFINER` Tenant Helper & Search-Path Pinning Verification
Every multi-tenant PostgreSQL schema MUST verify in its automated test suite that:
- Tenant lookup helpers (e.g., `public.current_user_organization_id()` / `public.current_user_tenant_id()`) are defined with `LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public SET row_security = off` to prevent infinite recursion when `public.profiles` enforces `FORCE ROW LEVEL SECURITY`.
- Function execution privileges are locked down via `REVOKE ALL ON FUNCTION ... FROM PUBLIC; GRANT EXECUTE ON FUNCTION ... TO authenticated, service_role;`.
- All `SECURITY DEFINER` functions explicitly pin `SET search_path = public`.
